# Mid-Course Project Reflection

This project helped me understand that API design is not only about adding fields or endpoints. Small choices define the contract clients rely on. Making `due_date` optional meant thinking through creation, updates, clearing, serialization, and invalid input. FastAPI and Pydantic handled much of the parsing and returned HTTP 422 for invalid dates, but I still had to decide what valid behavior meant for the application.

Keeping search and filtering on the server was an important design lesson. The frontend sends only active query parameters, and the backend remains the authority on which tasks match. Composing filters with AND logic made each condition predictable: every active filter narrows the same result set. I also learned to normalize text carefully so that case-insensitive partial search works while blank search or assignee values are ignored and unassigned tasks do not match a real assignee query.

On the frontend, preserving state during refreshes was more subtle than adding the controls. Create, edit, delete, and drag-and-drop all reload tasks, so those paths must reuse the active filters. Otherwise the interface appears to forget the user's context even though each individual feature works. Reusing the existing fetch and render flow kept this behavior consistent without changing the Kanban architecture.

The automated tests gave me confidence at boundaries that are easy to miss manually. The overdue Break Test demonstrated this clearly: changing `<` to `<=` made tasks due today overdue, and the tests detected it. The search Break Test showed that changing title matching from substring to equality broke the intended partial search while description search still worked. Seeing the exact relevant tests fail, then pass after restoration, was stronger evidence than simply reading the code.

AI assistance was useful for exploring implementation options, listing edge cases, and drafting repetitive changes. The risk is that a plausible response can still assume the wrong requirement, overstate verification, or disrupt existing behavior. I did not treat generated output as automatically correct. Reviewing diffs, checking the API contract, running tests, and manually exercising the browser prevented blind acceptance. Failed commands and broken-test results also needed to be recorded honestly rather than hidden.

If I continued the project, I would improve the separation of the filtering logic from in-memory storage so it could move more easily to a database query. I would also add configured frontend automated tests for query-string construction, filter-state persistence, and overdue rendering. Finally, I would make the manual verification process more repeatable with a short checklist tied directly to each acceptance criterion.
